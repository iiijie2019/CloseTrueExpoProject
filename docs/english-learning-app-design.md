**英语学习 App：可行性评估与产品、技术设计方案**

评估日期：2026-09-20。本文保留最初的可行性评估与长期设计；项目随后已实现首版业务功能，当前落地情况见下一段。原文中的双库、完整 sense 模型、词库构建流水线与性能数字仍属于后续设计，不能当成已完成验收。

**当前实现。** Word Grove（词间）使用亮色奶油绿与半透明卡片，底部为首页／我的两个 Tab。首页连接单词筛选、词根词缀和句子学习；单词为互斥三态，提供词性、音标、例句、变形、词族和 TTS。词库现有 200 个词条、32 组词根词缀，支持中英文界面及跟随系统。12 个句子练习提供彩色词块、成分说明、完整句子／词块朗读、替代语序和点选排列反馈。

当前采用静态 TypeScript 词库 + 原生 SQLite 单表存储个人数据；Web 使用独立 localStorage 适配。个人标记与词条以稳定 ID 关联，备份合并支持冲突选择与恢复副本。本次词库升级保持原来的 ID，旧备份继续可用。课程练习状态暂为当前页面内状态，不新增打卡或累计进度。

Expo Updates 已接入现有 EAS 项目，使用 fingerprint runtime 和 preview／production 通道，“我的”页支持检查、下载、保存完成后手动应用。原生安装包和真实 OTA 分发仍需按 [热更新说明](./expo-updates.md) 验证。[词库维护说明](./vocabulary-content.md) 记录内容范围及增补规则；README 提供当前目录结构与运行命令。

**1. 产品定位与评估结论。** 建议将产品定位为“通过词根和词族理解单词，并管理个人词汇掌握情况的离线英语学习工具”。默认面向中文使用者，首版以 iOS、Android 手机为目标，采用中文界面、英汉释义；Web 保留开发预览，正式支持单独验收。

用户的四项需求都可实现。工程上最需要提前确定的是词汇数据来源和学习状态的含义；长期工作量主要来自内容整理、词根关系审核和词库维护。

| 需求 | 可行性 | 建议实现 | 主要边界 |
| --- | --- | --- | --- |
| 已知、未知、关注 | 高，开发难度低 | 本地存储三个互斥状态，各入口保持一致 | 关注表示需要反复看的状态，不是独立收藏开关 |
| 词根词缀学习 | 高，内容难度较高 | 维护经过审核的词根、词缀和词族关系 | 字母相似不能证明同源，词形还原也不等于找词根 |
| 搜索展示词性 | 高 | 按词条列出名词、动词、形容词等，详情按词性分组 | 一个词可能有多种词性，不能只存一个字符串 |
| 读音、来历、用法、场景、变形 | 高，但取决于内容覆盖 | 结构化词典数据加中文精讲内容 | 不能承诺每个词都自动得到完整、准确的介绍 |
| 点击播放读音 | 高 | 首版系统 TTS，后续补充匹配词义和口音的词典音频 | 设备音色、静音状态和语言包影响效果 |
| 显示音标 | 高 | 独立存储词典提供的 IPA | TTS 接口不提供词典音标，二者分别实现 |
| 无登录、文件迁移 | 高 | 本地持久化数据库，加带版本的 JSON 导入导出 | 本地保存不能代替外部备份 |

推荐采用“离线词库 + 本地用户数据库 + 系统朗读”。首版运行不需要账号服务、业务服务器或付费 AI 接口。词库仍需要在开发阶段构建和校对。

**2. 当前项目适配情况。** 项目已经使用 Expo `~57.0.24`、React Native `0.86.3`、React `19.2.3`、Expo Router `~57.0.22` 和严格模式 TypeScript。`src/app/index.tsx`、`explore.tsx` 是模板页面，尚无词库、学习记录、文件迁移或朗读模块。现有明暗主题、路由和基础组件可以继续使用。

已按项目要求阅读 [Expo 57 版本文档](https://docs.expo.dev/versions/v57.0.0/)。该版本文档列出的 React Native 主版本为 0.86，与项目一致；后续依赖使用 Expo 的版本匹配安装方式，不套用旧版示例。新增业务不需要先降级或重建项目。

项目同时存在已跟踪的 `package-lock.json` 和未跟踪的 `pnpm-lock.yaml`。实施时需要统一包管理器；现阶段建议沿用已跟踪的 npm 锁文件，本轮不处理已有文件。

**3. 学习状态和统计口径。** 第一版遵循用户提出的三个互斥值。

| 状态 | 存储值 | 用户含义 | 交互 |
| --- | --- | --- | --- |
| 未知 | `unknown` | 还不认识，或暂时没有掌握 | 可改为关注或已知 |
| 关注 | `focus` | 想多看几遍，列入反复学习列表 | 可改为已知，也可退回未知 |
| 已知 | `known` | 用户自认为已经掌握 | 可以重新改为关注或未知 |

三个状态可以任意切换。阅读次数、播放次数和浏览详情都不自动把一个词改为已知。每次修改后显示轻量反馈，并提供撤销；首页、搜索、词根页和词库列表同时更新。

尚无用户记录的词按“未知”显示，不必为整个词典预先写入未知记录。只有用户明确选择状态或执行“加入我的词库”后，才创建个人词库记录；仅浏览只写最近浏览记录。这是存储和收录规则，不增加第四个学习状态。

首页“已知数量”和“关注数量”只统计个人记录，不能将整个内置词库的规模当成用户未掌握量。我的词库中的“未知”只统计用户主动收录的未知词。首次启动两项主数字均为 0。

第一版学习状态按词头对应的学习单元统计：`action` 的不同词性共用一份学习状态；复数 `actions` 若只是该词的屈折形式，则指向 `action`，不重复计数。`act`、`active`、`activity`、`action` 是不同学习单元，各自拥有状态。词形存在多个可能原词时展示候选，不能猜测后直接合并。

以后如确实需要“已知但仍关注”，再把掌握状态和关注标记拆开；第一版不引入这种与当前三态要求不同的行为。

**4. 信息架构与页面设计。** 底部使用四个入口：总览、查词、词根、我的词库。设置由总览右上角进入，避免没有账号功能却占用一个“个人中心”页。

| 页面 | 主要内容 | 核心操作 |
| --- | --- | --- |
| 总览 | 已知数量、关注数量、关注词预览、最近查看、词根学习入口 | 搜索单词、查看关注列表、继续上次查看的词族 |
| 查词 | 搜索框、最近搜索、匹配单词、词根结果 | 查看释义、播放、修改状态、进入详情 |
| 词根 | 词根／前缀／后缀切换、中文含义、关联词数量 | 按字母或关键词找词根，进入词族 |
| 我的词库 | 全部／关注／未知／已知，搜索和排序 | 集中学习、修改状态、查看详情 |
| 单词详情 | 发音、词性释义、构词提示、词源、用法、场景、词形、词族 | 听读音、标记状态、跳转关联词 |
| 词根详情 | 词根含义、常见形式、按词性分组的词族 | 连续查看同族词，按状态过滤 |
| 集中学习 | 来自关注列表或当前词族的单词卡片 | 显示释义、朗读、改状态、下一词 |
| 设置与数据 | 英美音偏好、语速、主题、导入导出、词库说明 | 备份恢复、清理缓存、查看来源 |

总览布局建议如下，数字仅为示意：

```text
总览                                      设置
[ 搜索单词或词根                            ]

[ 已知单词 128 ]        [ 关注单词 36       ]

继续看看关注的词                    查看全部 >
action       n. 行动；行为             关注
active       adj. 活跃的               关注
[ 开始浏览关注词 ]

从词根学习
act · 做、行动                  查看关联词 >

最近查看
activity     action     active

总览          查词          词根          我的词库
```

首次使用时用“搜索一个单词，或从词根开始”替代空列表。没有关注词时显示进入查词和词根学习的入口。不设置打卡、连续天数、排行榜、强制每日任务或推送提醒。

查词结果每行包含单词、常用词性、简明中文释义、朗读按钮和当前状态。词性使用“n. 名词”“v. 动词”“adj. 形容词”等可理解的标签；一个词有多种常用词性时同时展示，长内容在详情展开。

搜索顺序为：精确词头 → 明确的词形／拼写别名 → 词头前缀匹配；词根结果单独分组。例如搜 `actions` 时说明它是 `action` 的复数，搜 `act` 时先给出单词，再给出词根入口。词根关联来自内容数据，不来自前缀搜索结果。中文释义检索和拼写纠错可在后续扩展。

词根详情第一版使用分组列表，避免在小屏幕上默认呈现复杂关系网。每个词同时显示词性、释义和状态。词根内部可以显示“已知 3 / 收录 8”，并明确分母指当前词族，而非用户总体词汇量。

我的词库默认展示全部已收录词，可直接切换关注。支持最近修改、最近查看、字母顺序；关注学习默认优先展示较久未看的词，同分按加入时间排序。这是浏览顺序，不是遗忘曲线或记忆效果预测。

集中学习由用户主动开始。卡片正面展示单词、音标和播放按钮，点开后展示释义与构词提示；底部提供三个状态操作和“下一词”。本次可浏览全部或自行选择数量，随时退出，已完成的状态修改立即保留。退出或切卡不自动改变掌握状态。

**5. 单词详情与词根学习内容。** 详情按“先解决认识和使用，再补充来历”的顺序组织。

| 顺序 | 模块 | 设计要求 |
| --- | --- | --- |
| 1 | 单词、音标、英／美发音按钮 | 首屏可见；明确口音；音标缺失时如实提示 |
| 2 | 状态选择 | 已知／未知／关注三段控件，便于单手操作 |
| 3 | 词性和释义 | 按词性、义项分组，常用义优先 |
| 4 | 构词记忆 | 展示经过审核的词根词缀拆解、中文理解提示 |
| 5 | 常见搭配和用法 | 关联具体义项；需要时说明可数性、及物性或语体 |
| 6 | 例句和使用场景 | 场景标签、英文例句、中文译文，支持整句朗读 |
| 7 | 词形变化 | 复数、过去式、分词等，注明变化类型 |
| 8 | 相关词族 | 同根词、派生词分别标注，显示各自词性和状态 |
| 9 | 来历与来源 | 简明词源，可展开查看来源和许可信息 |

以 `action` 为例，可以这样组织内容：

- 常用名词义：行动、行为；还可按收录范围提供电影动作场面、法律行动等其他义项。
- 用法：`take action`、`put ... into action`；用法与对应义项绑定。
- 自拟学习例句：`Our team took action to reduce waste.`，译为“我们团队采取行动来减少浪费”。场景标记为工作／环保。
- 名词词形：`actions`。若收录动词义，则其 `actioned`、`actioning` 等单独放在动词分组，并注明商务等使用语境。
- 构词提示：可用 `act + -ion` 帮助记忆，但不把教学拆解当成完整历史来源。
- 来历简述：英语形式经过中古英语和古法语，可追溯至拉丁语表示“做、行动”的相关形式。

上述词性、词形和词源关系可见 [Wiktionary 的 action 词条](https://en.wiktionary.org/wiki/action)；示例句为本文自拟。该词并非只能作名词，因此数据和界面都不能把它锁定成单一词性。

词族页可以将 `act`、`active`、`activity`、`action` 放在同一个学习分组，分别展示名词／动词、形容词、名词等标签。只有核实了直接派生关系时才画“由 A 派生 B”的方向箭头，普通词族成员关系不暗示所有单词都由现代英语 `act` 直接拼接生成。

必须区分三类内容：词形变化是同一词的语法形式；派生词通常是不同词汇单位；词源介绍解释历史来源。助记故事若以后加入，标明“记忆提示”，不能伪装成词源。没有可靠拆解的词展示“暂未提供构词讲解”，保留已有释义和用法。

**6. 词汇数据方案。** 推荐在开发侧构建词库，并随 App 发布精选离线包。设备只读取整理后的结构化数据，无需在用户每次搜索时临时抓网页或生成解释。

| 候选来源 | 可提供的内容 | 适合的角色 | 本次判断 |
| --- | --- | --- | --- |
| Wiktionary／Wiktextract／Kaikki | 英文释义、词性、音标、词形、部分词源与关系 | 结构化离线词库的优先候选 | 字段不保证齐全；需筛选、清洗、翻译、审核 |
| ECDICT | 英汉释义、音标、词形、部分频率信息 | 中文基础释义的候选补充 | 需要核查数据来源与质量，不能当作完整精讲库 |
| Free Dictionary API | 官方示例包含释义、词性、音标和音频字段 | 可选在线补充或验证原型 | 不能据此承诺完整词根、中文讲解或所有词的词源 |
| 项目自编内容 | 中文构词讲解、场景、原创例句、易混说明 | 产品核心教学内容 | 可用工具辅助起草，但必须人工校对后发布 |

[Wiktextract 数据说明](https://github.com/tatuylonen/wiktextract)列出了 `sounds`、`forms`、`senses` 和 `etymology_text` 等字段，说明内容结构具备可实现性，但不等于抽样覆盖已通过。Kaikki 当前把旧的后处理下载标为弃用，构建管线应基于其 [raw data 下载入口](https://kaikki.org/dictionary/rawdata.html)固定具体快照，并筛出目标英语词条，不将整个原始数据集放进手机。

[ECDICT 项目说明](https://github.com/skywind3000/ECDICT)提供了中文释义、音标及词形字段，同时将音频、例句扩展列为待添加项；它的 README 也介绍了多种上游资料。因此本方案把它列为待核查候选，不仅凭仓库 MIT 标签就认定全部内容可直接用于正式发布。

[Free Dictionary API 官方页面](https://dictionaryapi.dev/)展示了词性和发音等返回结构，但本次没有进行批量调用、稳定性或目标地区网络测试。首版查词的可用性不应依赖这个接口。

词条来源需要保留名称、原始页面／版本、获取日期、许可标识和修改记录。使用 Wiktionary 派生文字时按相应许可处理归属及改编内容；音频和引用例句单独检查来源，不能假定与整页文字一致。参见其[内容版权说明](https://en.wiktionary.org/wiki/Wiktionary:Copyrights)。来源信息属于词库元数据，用户可在详情末尾或设置中查看。

建议设置两种内容完整度，但不把它们包装成两个付费等级：

- 基础词条：至少有词头、词性、中文释义；音标、词形按实际数据提供。
- 精讲词条：额外提供经过核实的构词关系、词源、常用搭配、场景和例句。

首个验证包建议为 100 个词、约 10 组词族，覆盖常见词、多词性词、多发音词、不规则变形和无法合理拆解的词。首次可发布版本可把内容目标暂定为 3,000 个基础词、300–500 个精讲词、50–100 个词根词缀条目；这些是规划目标，必须依据抽样结果和编辑资源调整，并非已经拥有的数据。

内容构建流程：

```text
固定来源快照
    ↓
筛选英语及首版词表 → 归一化词性、义项、发音和词形
    ↓
中文编辑与词根关系审核 → 来源、许可和缺失字段检查
    ↓
生成稳定 ID、索引、版本清单和校验值
    ↓
输出 dictionary.db + manifest.json + 来源说明
```

构建时校验关系指向存在、同词去重、义项与发音关联、必填字段、许可元数据及词形映射歧义。每次发布输出字段覆盖报告。AI 如参与内容制作，只用于开发侧辅助，未经确认的生成内容不直接进入正式精讲库。

**7. 朗读与音标实现评估。** 首版使用 `expo-speech` 调用系统 TTS，提供单词和例句朗读、英美音偏好及慢速／正常速度。Expo 57 的 [Speech 文档](https://docs.expo.dev/versions/v57.0.0/sdk/speech/)提供语音枚举、语言／音色设置、语速和停止等能力，并说明 iOS 真机静音模式可能导致无声。

用户点击播放时，先停止旧内容再播放新的内容，避免排队叠加；快速连续点击通过请求标识确保最后一次请求生效，过期回调不能改写新播放状态。离开页面或进入后台时停止播放。跨平台第一版采用播放／停止，不依赖暂停恢复行为。

默认尝试用户选择的 `en-US` 或 `en-GB` 音色。缺少指定口音时可使用现有英语音色，但界面应提示实际采用的口音；没有可用英语音色时提供清晰说明，不能误用中文声音读英文后仍标为英音。

系统 TTS 不按调用次数向本项目收费，但设备上某个声音能否离线使用取决于系统引擎和语言包，不能承诺所有手机均可断网朗读。[Android Voice 文档](https://developer.android.com/reference/android/speech/tts/Voice)明确区分声音是否依赖网络。需要在真实设备上验证；枚举到声音也不能直接视为离线可用证明。

IPA 从词库读取，按口音和必要的词性／义项保存多个发音记录。缺失时显示“暂无音标”。同形异音词需要特别处理：单独把字符串传给 TTS 不能保证得到当前词义的读音。因此系统朗读明确标为合成发音，不能声称与某条 IPA 严格匹配。

后续若要提高发音一致性，补充带来源许可、明确口音和词义的词典音频，使用 SDK 57 的 [expo-audio](https://docs.expo.dev/versions/v57.0.0/sdk/audio/) 播放。匹配的本地音频优先；可选联网音频在允许联网时使用；失败后再降级至系统朗读，并显示来源类型。同形异音词没有匹配音频时，不伪装成已解决准确发音问题。

首版只播放，不需要录音或语音识别。音标展示、单词 TTS、例句 TTS 分别验收，不将其中一个可用当成其余均可用。

**8. 本地存储和数据迁移。** “无登录、数据存在手机里”完全可行，但学习记录应该放在应用持久化数据库，而非可清理缓存。缓存只保存能重新获得的音频和临时导入导出文件。

推荐两个 SQLite 数据文件：

| 文件 | 内容 | 更新方式 |
| --- | --- | --- |
| `dictionary.db` | 单词、义项、发音、词形、词根关系、精讲内容 | 随内容包版本更新，运行时按只读用途使用 |
| `user.db` | 学习状态、收录信息、最近浏览、设置和迁移版本 | 随用户操作写入，与词库升级分离 |

[Expo SQLite 57](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/)支持持久化数据库、异步访问、事务以及全文检索扩展，适合上述关系数据。词典不能只作为巨大 JSON 在启动时全部加载；个人记录也不宜分散成大量难以统计和迁移的零散键值。

首次启动准备词库并迁移用户表，成功后进入首页。词库升级生成新版本文件、检查完整性后切换，保留旧版本用于失败恢复。用户库迁移按顺序执行、带事务；迁移失败进入可恢复错误页，不能直接清空学习记录。

导出格式采用 UTF-8 JSON，文件名例如 `english-learning-backup-2026-09-20.json`。包含以下信息：

| 字段 | 用途 |
| --- | --- |
| `format`、`schemaVersion` | 识别本 App 的备份格式并选择迁移逻辑 |
| `appVersion`、`exportedAt` | 显示生成版本和导出时间 |
| `dictionaryVersion` | 判断恢复时的词库匹配情况 |
| `records` | 稳定单词键、语言、词头快照、状态、收录和更新时间 |
| `settings` | 口音偏好、主题、语速等可迁移设置 |
| `history` | 可选最近浏览，默认不导出 |

不导出全部词典释义、可重建搜索索引或音频缓存。换设备导入时，恢复对应内置词的个人数据；源设备中有而目标词库暂时没有的记录，保留词头快照和原始键，标为“待匹配词条”，不能静默丢弃。以后找到匹配项再恢复关联。不同平台的具体音色 ID 不直接强制沿用，迁移语言偏好后在目标设备重新匹配。

导入流程：选择文件 → 检查格式、版本、大小及记录 → 预览新增／重复／冲突／待匹配数量 → 用户选择策略 → 建立本地恢复点 → 在事务中写入 → 重算统计并显示结果。

默认策略为“合并，冲突保留本机”，可以改为“合并，冲突使用导入记录”。可另外提供“用备份替换个人数据”，此操作需在产品界面明确说明影响并由用户确认。不能仅比较两个设备时间就静默裁定谁更新，因为设备时钟可能不一致。合并不推断删除；替换才表达恢复到完整备份状态。

重复导入同一份文件不能重复计数。文件格式不支持、损坏或字段不合法时不写入；写入失败整体回滚。对未来版本备份拒绝盲目处理，提供升级提示。首版建议设定 20 MB、100,000 条个人记录的保护上限，并在读取前尽可能检查文件大小；具体阈值需按设备测试调整。

文件实现使用 SDK 57 的 [FileSystem：File／Directory／Paths](https://docs.expo.dev/versions/v57.0.0/sdk/filesystem/)。通过 [DocumentPicker](https://docs.expo.dev/versions/v57.0.0/sdk/document-picker/) 选择备份并复制至临时缓存读取，解析完成后保存到用户数据库；通过 [Sharing](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/) 打开系统导出面板。分享面板关闭不代表用户已经成功保存到外部，界面只能确认已生成文件或已打开导出面板，不能误报外部备份完成。

设置中区分“清理缓存”和“重置学习数据”，前者不影响状态。正常关闭和重启不丢记录；卸载、系统清除应用数据或设备损坏则不能依赖本机副本恢复。自动生成的本机恢复点有助于撤销导入，但跨设备迁移和卸载前保留仍需要用户导出到外部位置。

**9. 数据模型。** 采用“词汇内容”和“个人学习记录”分离的模型。下表是逻辑设计，实施时可适度合并纯展示内容表，避免为了抽象而拆出过多层。

| 逻辑表 | 关键字段与责任 |
| --- | --- |
| `words` | `word_key`、`language`、`headword`、`lookup_key`、简明释义；代表可标记的学习单元 |
| `entries` | `entry_id`、`word_key`、`pos`、词源分组；允许一个词有多个词性和同形异义词条 |
| `senses` | `sense_id`、`entry_id`、中英文释义、语体、可数性／及物性、展示顺序 |
| `pronunciations` | `pronunciation_id`、`entry_id`、可选 `sense_id`、口音、IPA、可选音频与来源 |
| `word_forms` | `entry_id`、`form`、变化类型、检索键；一个形式允许映射多个词条 |
| `morphemes` | 稳定 ID、类型 root／prefix／suffix、显示形式、变体、中文含义、来源 |
| `word_morphemes` | `entry_id`、词素 ID、显示顺序、拆解提示、审核状态；多对多关联 |
| `word_relations` | 起止词条、关系类型、说明、来源；区分直接派生、同族和拼写变体 |
| `usage_items` | `sense_id`、搭配、例句、译文、场景标签、使用说明、来源 |
| `etymologies` | 词源分组、中文简述、扩展内容和来源 |
| `sources`、`content_sources` | 许可、来源 URL／版本、作者或归属信息，关联到具体内容 |
| `word_aliases` | 旧词键到新词键的明确映射；用于内容版本迁移 |
| `user_word_states` | `word_key` 主键、语言及词头快照、三态、收录与更新时间、修订号 |
| `recent_views` | `word_key`、最后查看时间；独立于是否收录，建议最多 100 条 |
| `settings` | 经过类型校验的偏好；不混入词典正文 |
| `schema_migrations` | 用户库已执行的迁移记录 |

`word_key` 由项目自己的稳定标识注册表维护，不能使用每次重新导入都会变化的行号。大小写归一化只用于检索；不能因此把 `US` 与 `us` 等语义不同的词头合成同一个标记单元。词源、义项和来源 ID 也不应借助数组位置生成长期引用。

词典库内部可用外键约束；用户库对词典词键的关联由应用验证和版本映射维护，不建立跨文件外键。缺少对应词典记录时保留个人状态，确保词库删改不会连带丢失用户数据。待匹配记录单独显示数量，在完成关联前不重复合并进多个词头。

必要索引包括词头查询键、词形查询键、词根成员，以及用户状态和更新时间。英文字头检索优先使用等值／前缀索引。后续有全文检索需求再引入 FTS；中文不能假设默认英文分词器就能获得理想检索效果。

**10. 项目代码架构。** 沿用 Expo Router 与 TypeScript，页面按功能组织，数据库与设备能力封装在边界清晰的模块中。暂时不需要后端、Redux、大型依赖注入框架或通用插件系统。

```text
src/
  app/
    _layout.tsx                  # 启动准备、应用提供者、根 Stack
    (tabs)/
      _layout.tsx                # 四个主入口
      index.tsx                  # 总览
      search.tsx                 # 查词
      roots.tsx                  # 词根词缀列表
      vocabulary.tsx             # 我的词库
    word/[wordKey].tsx           # 单词详情
    root/[morphemeId].tsx        # 词根详情
    review.tsx                  # 用户主动发起的集中学习
    settings/index.tsx
    settings/data.tsx           # 导入导出
    settings/sources.tsx

  features/
    overview/                   # screen、components、hooks
    search/
    word-detail/
    roots/
    vocabulary/
    review/
    settings/
    backup/

  domain/
    vocabulary.ts               # 词、义项、词形、关系类型
    learning.ts                 # 三态、统计和学习单元规则
    backup.ts                   # 备份格式及冲突策略

  data/
    db/
      dictionary.ts             # 词库准备与版本切换
      user.ts                   # 用户库连接、写入调度
      migrations/
    repositories/
      dictionary-repository.ts
      learning-repository.ts
      history-repository.ts
      settings-repository.ts
    queries/                    # 页面查询、缓存和失效订阅

  services/
    pronunciation-service.ts    # 统一播放入口、音色选择、停止与降级
    backup-service.ts           # 校验、预览、导入和导出
    dictionary-service.ts       # 词形映射、词族装配等组合查询

  platform/
    speech.native.ts
    speech.web.ts
    files.native.ts
    files.web.ts

  components/
    ui/                         # Button、Card、Chip、EmptyState 等
    WordRow.tsx

  schema/                       # 内容字段约束
  manifests/                    # 来源、版本、许可和覆盖报告

scripts/dictionary/             # 清洗、校验、索引和数据库构建

```

路由文件只负责参数解析和页面装配，具体界面在 `features`。根 Stack 包含 Tabs、单词详情、词根详情等，详情页不成为额外 Tab。当前原生标签和 `.web.tsx` 的平台拆分可以继续沿用；原生实现以 [SDK 57 Native Tabs](https://docs.expo.dev/versions/v57.0.0/sdk/router/native-tabs/) 为准。

依赖方向：页面／功能 hooks → 业务服务或 repository → SQLite／系统能力。单纯的读取可直接使用 repository；跨表状态变更、备份和播放调度通过服务封装。domain 不依赖 React Native，UI 不直接执行 SQL，也不直接调用 TTS。

学习状态的唯一持久化真相在 SQLite。界面使用普通 React 状态保存搜索输入、当前筛选和展开状态。提供一个小型公共查询订阅层，仓储提交写入后发布变更，相关页面重新查询；不要在每个页面维护一份互相独立的词状态副本。随着查询复杂度增加再考虑引入专用查询缓存库。

一次状态修改：

```text
点击“关注”
    → 校验目标词键和状态
    → 用户库事务写入／更新
    → 提交成功后通知详情、列表和总览刷新
    → 提供撤销，撤销也作为一次新的持久化操作
```

首版可选择“等待本地提交后显示成功”，降低乐观更新回滚复杂度。连续写入集中调度；导入期间暂停个人记录修改，避免覆盖。SQL 使用参数绑定。列表批量读取状态，避免一行发一次数据库查询；异步搜索使用请求序号忽略过期结果，防止较旧查询覆盖新输入。

新增依赖优先只有 `expo-sqlite`、`expo-speech`、`expo-file-system`、`expo-document-picker`、`expo-sharing`；引入词典音频时再增加 `expo-audio`。具体版本由 SDK 57 的安装工具解析。本轮未安装依赖。

**11. 视觉与交互规范。** 整体采用安静、清晰的阅读工具风格，以词汇内容为主。建议默认跟随系统明暗主题，浅色使用暖白背景、深色使用深灰背景；主操作用蓝色，已知用绿色，关注用琥珀色，未知用中性色。状态同时提供文字或图标，不仅用颜色表达。

建议以 8 点间距为基础，页面左右留白 20–24，正文 16–17，词头 30–34，解释正文保持足够行距。卡片圆角约 12–16，不为装饰压缩例句和释义。中文采用系统字体，英语词头可增加字重；音标使用经过 IPA 字形检查的字体，并验证重音符号与组合附加符号显示。

播放按钮和状态按钮保持至少 48 逻辑像素的可点击区域；支持系统大字体、屏幕阅读器标签和减少动画偏好。单词详情中的文本允许选择复制。词源和较少见义项默认折叠，释义与发音不折叠。状态修改有反馈但不弹窗，危险的数据替换操作才使用确认流程。

应用异常状态与文案也应在首版完成：

| 场景 | 用户看到的内容 | 数据行为 |
| --- | --- | --- |
| 未收录查询词 | 当前离线词库未收录；提供相近词或清除输入 | 不生成未经验证的释义 |
| 无音标／词源／构词讲解 | 在对应位置简洁说明暂无内容 | 保留已有模块 |
| 无英语音色／朗读失败 | 播放失败原因和重试入口 | 不影响阅读与标记 |
| 写入失败 | 本次修改未保存，可重试 | 不显示已成功的假状态 |
| 导入文件不合法 | 说明文件或版本问题 | 不修改当前数据库 |
| 词库缺少备份中的单词 | 待匹配词条列表和数量 | 保留用户原始记录 |
| 首次准备或升级词库 | 进度或准备提示；失败可重试 | 保留上一个可用版本 |

**12. 平台与性能边界。** iOS、Android 为正式功能目标。Expo SQLite 的 [Web 支持目前标记为 alpha](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/#web-setup)，还涉及 WASM 和响应头配置；当前项目虽能运行 Web 模板，也不能据此承诺本地数据库行为完全相同。Web 若正式发布，需要单独设计浏览器存储、数据清理提示和下载导出适配。

原生本地文件 URI 的分享方式不能直接照搬到 Web，Expo 的 [Sharing 平台说明](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/)明确区分这些能力。因此 Web 导出应在后续通过浏览器下载能力实现，不为了文件迁移自动上传用户数据。

性能验收目标先作为测试标准，不当作已有结果：在约定的中档设备、首版词库和 10,000 条个人记录下，词头检索 P95 争取低于 150 ms（不含约 150 ms 的输入防抖），详情本地数据读取低于 200 ms，状态提交及可见统计更新低于 200 ms。首次词库准备单独测量并显示等待状态。

列表使用虚拟化和分页，不一次渲染全部词条；首页只读统计和少量预览；词库构建在开发侧完成。实测若未达目标，再针对索引、分页和批量查询优化。包体大小需在真实词库构建后测量；首版不打包全量真人音频。

**13. 分阶段实施和验收。** 建议先验证内容和持久化，再完成完整交互。

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：内容与设备验证 | 100 词样本、10 组词族、字段覆盖报告、iOS／Android 朗读实验 | 验证来源可用性，明确缺失信息和音色限制 |
| B：基础学习闭环 | 本地双库、搜索、单词详情、三态、总览统计、我的词库 | 查词→标记→统计更新→重启保留全程可用 |
| C：词根与精讲 | 词根入口、词族列表、构词解释、词形、例句和场景 | `act` 相关学习链路完整，关系与词性正确 |
| D：集中学习与迁移 | 关注卡片、设置、导入预览、合并／替换、恢复点 | 两台设备迁移成功，重复导入与异常文件不损坏数据 |
| E：发布完善 | 扩充通过审核的内容、明暗主题、大字体、性能与真机验证 | 功能、内容和迁移验收均通过 |

时间只适合给粗估：在一名熟悉 Expo 的开发者、内容结构已确定、无后端的前提下，工程闭环约需 3–5 个工作周；成批精讲内容编辑、第三方授权、商店流程和新增 Web 支持另计。应在阶段 A 完成后重新估算，不能用 App 页面开发时间代表词库制作时间。

必要的验证集中在用户数据和内容正确性，而非为每个展示组件编写重复测试：

- 三态任意切换、重复点击和撤销后，详情／搜索／首页一致；重启后保存正确。
- 默认未知不膨胀个人词库；`actions` 归入 `action` 的计数；不同派生词独立计数。
- 同形异义、多词性、不规则词形、大小写敏感词头和歧义映射不被误合并。
- 导出后跨设备恢复；合并冲突策略正确；重复导入幂等；非法／未来版本文件无副作用；中断写入能回滚。
- 更换词库版本保留学习状态，缺失词键进入待匹配状态，迁移失败不清库。
- 在 iOS 真机静音／非静音、Android 不同语音引擎、断网及缺少指定音色时验证朗读；多次点播和离开页面不出现错乱播放。
- 所有精讲构词关系经人工审核；来源可追溯；缺失内容不伪造；典型音标和例句无排版缺字。
- 在约定数据量下测量搜索、滚动、启动和导入行为，并验证明暗主题及大字体。

**14. 本方案采用的默认决策。** 无登录、无打卡、无自动同步；首页突出已知和关注数量；学习状态为互斥三态；个人数据持久化在 SQLite；首版内置精选离线词库和系统 TTS；音标单独由词库提供；词根关系和精讲在开发侧审核；文件迁移优先实现，云服务和在线 AI 讲解留作未来独立需求。

尚未通过实测确定的事项为：候选词库的目标词表覆盖率、中文释义质量、正式发布的数据使用条件、设备语音可用性、构建后的包体与性能。阶段 A 用样本和设备实验解决这些问题，之后再确定发布内容规模。
